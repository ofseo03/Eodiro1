# 구현 메모

`docs/spec.md` 를 구현하면서 확정한 사항과, 아직 검증하지 못한 사항을 구분해 기록한다.

## 1. 구조

```
lib/
  types.ts            도메인 타입
  constants.ts        도보 상한·교체 반경·날씨 기준값
  geo.ts              직선거리와 보행거리 추정
  data/               지역·태그·장소 데이터와 PlaceProvider
  weather/            기상청 단기예보 격자 변환·클라이언트·판단
  routing/            보행 경로/대중교통 경로 provider 인터페이스
  engine/             구간 계획(leg) · 코스 구성(course) · 추천 · 교체 · 입력 검증
app/api/
  recommend           조건으로 코스를 추천한다
  replace             한 장소의 교체 후보를 찾는다
  course              교체 후 코스를 다시 계산한다
```

외부 데이터는 모두 provider 인터페이스 뒤에 둔다. 엔진과 화면은 어떤 API를 쓰는지 알지 못하므로,
공공 API를 연동할 때 엔진을 고치지 않고 provider 구현만 추가하면 된다.

## 2. 스펙 7절의 미확정 항목 중 이번에 확정한 것

| 항목 | 확정 내용 |
| --- | --- |
| 초기 취향의 선택 항목 | 코스 구성 카테고리, 선호 태그, 기피 태그 |
| 취향 저장 방식 | 기기 내 저장(localStorage, 키 `eodiro:preferences:v1`). 계정 기반 저장은 도입하지 않았다. |
| 한 코스의 장소 수와 구성 | 사용자가 고른 카테고리 수만큼(2~3곳). 방문 순서는 엔진이 정한다. |
| 지역 경계 정의 | 중심 좌표와 반경으로 근사한다(`lib/data/regions.ts`). 행정동 경계는 도입하지 않았다. |
| 방문 시각 입력 | `datetime-local` 로 받는다. 출발 위치는 별도로 받지 않고 지역 중심을 날씨 기준 위치로 쓴다. |
| 덥다·춥다·비 예보 기준 | 기온 28℃ 이상 / 4℃ 이하 / 강수형태가 있거나 강수확률 60% 이상 (`WEATHER_THRESHOLDS`) |
| 100m 내 교체 후보가 없을 때 | 안내만 하고 반경을 넓히지 않는다. |
| 정류장 접근·환승 도보 | 구간별 최대 도보 거리를 적용하지 않고 거리만 표시한다. 대중교통 provider를 연동한 뒤 재검토한다. |

기본값은 구간별 최대 도보 거리 600m, 총 이동시간 상한 45분으로 두었다.

## 3. 거리·시간을 다루는 규칙

스펙 3절의 "거리·시간의 정확성"을 코드에서 다음과 같이 강제한다.

- 모든 거리·시간 값에 `verified` / `estimated` / `unknown` 신뢰도를 붙인다.
- 실제 보행 경로를 확인하지 못하면 직선거리 × 1.3 을 추정 보행거리로 쓰고, 최대 도보 거리
  충족 여부는 `확정 불가`로 남긴다. 화면에도 "직선거리 기준 추정"으로 표시한다.
- 미확인 구간의 시간을 0분으로 더하지 않는다. 확인된 구간만 합해 "확인된 구간 이동시간 합계"로
  표시한다.
- 총 이동시간 상한은 모든 구간이 `verified` 이고 합이 상한 이내일 때만 `충족`으로 표시한다.
  확인된 구간만으로 이미 상한을 넘으면 `미충족`이 확정된다. 그 외에는 `확정 불가`다.
- '경로 없음'(정상 조회 결과), '경로 조회 실패'(API 오류·시간 초과), '경로 조회 미구성'(provider
  미연동)을 서로 다른 상태로 구분한다. 조회 실패만으로 택시 대안으로 전환하지 않는다.
- 날씨를 확인하지 못하면 '날씨 미반영'으로 표시하고, 실내 우선 추천을 적용하지 않는다.
- 복합·미확인 장소를 실내로 단정하지 않는다. 실내 우선 조건에서 실내 장소보다 낮은 점수를 준다.

## 4. 아직 검증하지 못한 것

이 작업 환경에서는 `data.seoul.go.kr`, `apis.data.go.kr`, `map.seoul.go.kr` 로 나가는 요청이 막혀
있어 실제 응답을 확인하지 못했다. 스펙 5절의 "실제 호출로 검증한 기능"에는 아직 아무것도 넣지 않는다.

| 대상 | 상태 |
| --- | --- |
| 서울시 관광 문화 데이터 | 미연동. `lib/data/sample-places.ts` 의 샘플 데이터를 쓰고 화면에 그 사실을 표시한다. |
| 기상청 단기예보 | 클라이언트는 작성했으나 실호출 미검증. `KMA_SERVICE_KEY` 가 없으면 '날씨 미반영'으로 동작한다. |
| 대중교통환승경로 / 최단경로 | 미연동. 버스·지하철 구간은 '경로 조회 미구성'으로 표시한다. |
| 보행 경로·실제 보행거리 | 확인된 공공 API가 없어 미연동. 추정값만 사용한다. |
| 택시 | 경로·소요시간 API를 쓰지 않는다. '택시 이용 검토 · 소요시간 미확인'만 표시한다. |

그래서 현재 화면에서 조건 충족이 확정되는 코스는 나오지 않는다. 이는 버그가 아니라 검증하지 못한
값을 확정으로 표시하지 않기 위한 의도된 동작이다.

## 5. 다음 단계

1. 서울시 관광 문화 데이터의 실제 서비스명·필드·좌표 제공 여부를 확인하고 `PlaceProvider` 구현 추가
2. 기상청 단기예보 인증키로 실호출을 검증하고, 격자 변환 결과를 실제 응답과 대조
3. 대중교통 API의 소요시간 필드에 접근 도보·환승·대기가 포함되는지 확인 후 `TransitProvider` 구현
4. 실제 보행거리를 제공할 수 있는 경로원을 찾고 `WalkRouteProvider` 구현. 이때부터 최대 도보 거리
   충족을 확정할 수 있다.
